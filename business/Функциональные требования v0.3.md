## 1. Общая концепция пользовательского сценария

«Арена переговоров» — веб-приложение для индивидуальной тренировки переговоров через управленческие поединки с AI-оппонентом.

Основной пользовательский цикл:

**Авторизация → выбор кейса → выбор ролевого сочетания → подготовка → поединок → транскрибация → судейство → тренерский разбор → повторная попытка**

В MVP пользователь играет только против AI. Библиотека содержит заранее подготовленные и методически проверенные командой кейсы. Администратор может настраивать контекст симуляции в пределах предусмотренных параметров.

---

# 2. Авторизация

### FR-AUTH-01. Авторизация пользователя

Система должна требовать авторизацию перед началом работы с тренажёром.

### FR-AUTH-02. Пользовательская сессия

После авторизации система должна идентифицировать пользователя в течение всей сессии прохождения кейса.

### FR-AUTH-03. Сохранение текущего прохождения

Система должна сохранять как минимум данные текущей подготовки и текущего поединка пользователя.


---

# 3. Библиотека кейсов

### FR-CASE-01. Список кейсов

Пользователь должен иметь возможность просматривать список доступных переговорных кейсов.

Для каждого кейса отображаются как минимум:

- название;
- краткое описание;
- персонажи;
- ориентировочная сложность;
- тип ситуации.

### FR-CASE-02. Просмотр кейса

После выбора пользователь должен видеть полный общий текст ситуации.

### FR-CASE-03. Персонажи кейса

Каждый кейс должен содержать не менее двух доступных персонажей.

Например:

> Менеджер по продажам
> 
> Генеральный директор
> 
> HR

### FR-CASE-04. Выбор ролевого сочетания
Для каждого кейса заранее задаются **доступные ролевые сочетания**.

Перед подготовкой пользователь выбирает одно из доступных сочетаний и определяет, какую роль играет самостоятельно, а какую — AI-оппонент.

### FR-CASE-05. Методическая конфигурация кейса

Для каждого кейса задаются:

- общая информация ситуации, доступная всем участникам;
- персонажи;
- доступные ролевые сочетания;
- подготовка каждой игровой роли;
- скрытая информация, доступная только соответствующей стороне;
- возможные исходы и значимые последствия решений.

Структура подготовки роли определяется документом [Подготовка к роли](business/Подготовка%20к%20роли.md)

**Подготовка AI-оппонента скрыта от пользователя. Подготовка пользователя недоступна AI-оппоненту.**

# 4. Подготовка к переговорам
**Пользователь может перейти к поединку в любой момент, не заполняя карточку подготовки полностью и не отправляя её AI на проверку. Все поля подготовки являются необязательными**
## 4.1. Структура карточки
### FR-PREP-01. Карточка подготовки
Система должна предоставлять пользователю цифровую карточку подготовки к выбранной роли.

Структура и определения элементов подготовки задаются документом **[Подготовка к роли](business/Подготовка%20к%20роли.md)**.

Карточка состоит из трёх основных блоков.

**Анализ ситуации**

- корневой конфликт;
- стратегическая цель ситуации;
- предложения, решающие конфликт.

**Стратегия**

- анализ по слоям переговоров;
- SWOT-анализ;
- цель на переговоры;
- заявляемая позиция (ЗП);
- желаемая позиция (ЖП);
- красная черта (КЧ);
- BATNA.

**Тактика**

- сценарий;
- загрузка.

Все поля подготовки пользователя являются необязательными. Пользователь может перейти к поединку на любом этапе подготовки.

# 5. AI-помощник при подготовке
### FR-PREP-02. Поэтапная проверка

Пользователь не должен отправлять AI всю карточку целиком.

Карточка разбивается на логические блоки, которые можно последовательно отправлять AI на проверку.

Например:

`Корневой конфликт → проверить`

затем:

`Стратегическая цель → проверить`

затем:

`Предложения → проверить`

и т. д.

### FR-PREP-03. Обратная связь

После отправки блока AI должен:

1. проанализировать ответ;
2. указать сильные стороны;
3. найти слабые места;
4. задавать уточняющие вопросы;
5. предлагать направления улучшения.

AI не должен просто заполнять подготовку вместо пользователя.

### FR-PREP-04. Редактирование

После получения обратной связи пользователь может изменить свой ответ и повторно отправить его AI.

### FR-PREP-05. Финальная подготовка

Все заполненные пользователем элементы должны сохраняться и быть доступны после переговоров.

Это необходимо, чтобы тренер после игры мог сравнить:

> «Что пользователь собирался делать»
> 
> с
> 
> «Что пользователь реально сделал».

Например, если пользователь сформулировал определённую стратегическую цель, но во время поединка начал решать задачу, навязанную оппонентом, это должно быть отражено в разборе.

# 6. Формат поединка

**Один поединок состоит из одного раунда продолжительностью максимум 5 минут**

## 6.1. Распределение игроков

### FR-GAME-01. Право выбора ролей

В поединке используются роли, выбранные пользователем перед этапом подготовки

### FR-GAME-02. Загрузка

Пользователь начинает поединок. Его первая реплика является загрузкой.

---
# 7. Голосовые переговоры

### FR-VOICE-01. Голосовой ввод

Пользователь должен вести переговоры голосом.

### FR-VOICE-02. Распознавание речи

После окончания реплики система преобразует речь пользователя в текст и передаёт распознанный текст AI-оппоненту.
Окончание реплики определяется системой автоматически по паузе в речи пользователя

### FR-VOICE-03. Голосовой ответ

Ответ AI преобразуется в речь и воспроизводится пользователю.

Для MVP используется последовательная модель:

**пользователь говорит → заканчивает → AI отвечает → заканчивает → пользователь отвечает.**

### FR-VOICE-04. Контекст

AI должен учитывать весь предыдущий диалог текущего раунда.

---

# 8. Поведение AI-оппонента

Это один из самых важных блоков продукта.

### FR-AI-01. Собственная позиция

AI не должен просто реагировать на сообщения пользователя.

Он должен играть конкретного персонажа с собственными:

- целями;
- интересами;
- картиной ситуации;
- ограничениями;
- приоритетами;
- отношением к другим персонажам.

### FR-AI-02. Устойчивость позиции

AI не должен необоснованно соглашаться с пользователем только потому, что тот настойчиво просит или хорошо формулирует предложение.

### FR-AI-03. Границы позиции

 Для AI-оппонента в каждом ролевом сочетании заранее задаются жёсткие границы переговорной позиции: Заявляемая Позиция (ЗП), Желаемая позиция (ЖП) и Красная Черта (КЧ). AI должен вести переговоры в пределах заданных границ и не принимать решения, выходящие за них.

### FR-AI-04. Последовательность

AI должен помнить собственные заявления, договорённости и уступки и не противоречить им без причины.

### FR-AI-05. Управленческое сопротивление

AI должен уметь:

- задавать неудобные вопросы;
- отстаивать свою позицию;
- менять аргументацию;
- требовать конкретики;
- предлагать альтернативы;
- реагировать на давление;
- принимать и отвергать предложения.

### FR-AI-06. Обязательное продолжение

AI **не может самостоятельно закончить раунд раньше времени**.

Даже при конфликтном поведении пользователя AI должен оставаться в роли до завершения раунда.

---

# 9. Таймер и завершение раунда

### FR-TIME-01. Максимальная длительность

Один раунд длится максимум **5 минут**. Отсчёт пяти минут начинается после нажатия пользователем кнопки «Начать»

### FR-TIME-02. Таймер

Во время раунда пользователь должен видеть оставшееся время.

### FR-TIME-03. Автоматическое завершение

При достижении 00:00 система:

- немедленно прерывает текущую реплику AI-оппонента
- останавливает переговоры;
- воспроизводит сигнал окончания;
- фиксирует конец раунда.

### FR-TIME-04. Досрочное завершение

Пользователь должен иметь возможность в любой момент досрочно завершить раунд нажатием кнопки «Завершить раунд»

---

# 10. Транскрипция

### FR-TRANS-01. Полная транскрипция

Система должна сохранять текст переговоров.
Фиксируются:
- участник;
- его роль;
- текст;
- временная отметка.

### FR-TRANS-02. Использование транскрипта

Транскрипт используется:

- AI-судьями;
- AI-тренером;

### FR-TRANS-03. Просмотр пользователем

После завершения каждой реплики её текст отображается пользователю в интерфейсе поединка в формате сообщения чата.

### FR-TRANS-04. Цитирование

Судьи и тренер должны иметь возможность ссылаться на конкретные фрагменты:

> `02:17 — «Давайте тогда договоримся...»`

---

# 11. Определение исхода переговоров

Это отдельный модуль и **не должен смешиваться с оценкой навыка игрока**.

### FR-OUT-01. Исход

После завершения поединка система должна определить фактический исход переговоров.

Например:

- договорённость достигнута;
- частичная договорённость;
- решение отложено;
- договорённость не достигнута.

### FR-OUT-02. Содержание результата

Если стороны договорились, система должна извлечь:

- кто что обязался сделать;
- сроки;
- условия;
- уступки сторон;
- последствия невыполнения, если они обсуждались.

### FR-OUT-03. Качество результата

Факт достижения договорённости **не означает автоматически хорошую игру**.

Игрок может добиться соглашения, но:

- слишком дорого заплатить;
- испортить отношения;
- взять необоснованные обязательства;
- отказаться от собственной цели.

Это непосредственно соответствует принципу гайда: необходимо учитывать не только результат, но и **цену результата и дальнейшие последствия**.

# 12. Судейство управленческого поединка

После завершения поединка действия участников оценивают судьи.

Нужны **три независимых AI-судьи**. Каждый судья получает общий текст кейса, выбранное ролевое сочетание и транскрипт поединка, но использует собственные инструкции и критерии коллегии

Критерии трёх коллегий не конкурируют: один эпизод может быть сильным для одной коллегии и слабым для другой.

## Судья №1 — Нанимающиеся на работу

### FR-JUDGE-01

Судья отвечает на вопрос:

> **«К кому из этих двух руководителей я бы пошёл работать?»**

Особое внимание:

- надёжность;
- отношение к людям;
- управленческая твёрдость;
- забота о команде;
- долгосрочные последствия управления.

## Судья №2 — Отправляющие на переговоры

### FR-JUDGE-02

Судья отвечает:

> **«Кого из этих двух игроков я отправлю вместо себя на сложные переговоры?»**

Особое внимание:

- движение к цели;
- управление другой стороной;
- работа с картиной мира;
- управление ролями;
- сохранение отношений.

## Судья №3 — Доверяющие собственность

### FR-JUDGE-03

Судья отвечает:

> **«Кому я готов доверить свои деньги, компанию или другой значимый ресурс?»**

Особое внимание:

- качество решений;
- компетентность;
- ответственность;
- риски;
- последствия для ресурсов.

---

# 13. Формат ответа судьи

### FR-JUDGE-04. Независимость

Каждый судья формирует решение независимо от других.

### FR-JUDGE-05. Обязательный выбор

Судья должен выбрать:

- Пользователя;
- ИИ-оппонента.

### FR-JUDGE-06. Доказательство

Вердикт не может быть просто:

> «Пользователь был увереннее».

Он должен быть подтверждён действиями и последствиями.

### FR-JUDGE-07. Формат комментария

Ответ строится по структуре методички:

**Мой выбор → наблюдение → эффект → сравнение.**

Например:

> **Выбор:** отправил бы на переговоры пользователя.
> 
> **Наблюдение:** на 03:14 он задал вопрос о причине требования.
> 
> **Эффект:** после этого выяснился реальный интерес оппонента, и разговор перешёл от требования к поиску вариантов.
> 
> **Сравнение:** AI-оппонент чаще принимал рамку оппонента и реагировал на его предложения.

# 14. Тренерский разбор

Это должен быть **отдельный AI-агент/вызов**, а не продолжение судейства.

### FR-COACH-01. Общий анализ

AI-тренер анализирует действия пользователя по ходу переговоров.

### FR-COACH-02. Анализ подготовки
Если пользователь выполнял подготовку, AI-тренер сопоставляет её с реальным поведением в поединке.

В зависимости от заполненных пользователем элементов анализируется:

- двигался ли пользователь к своей цели на переговоры;
- соответствовали ли его действия выбранному сценарию;
- использовал ли он подготовленные вопросы, аргументы и варианты решений;
- насколько фактическое начало разговора соответствовало подготовленной загрузке;
- как изменялась его переговорная позиция;
- какие уступки он сделал и что получил взамен;
- не нарушил ли собственную красную черту;
- сохранил ли BATNA как реальную альтернативу;
- насколько итог соответствует желаемой позиции;
- какие элементы первоначальной подготовки оказались ошибочными или потребовали изменения по ходу разговора.

Тренер не должен считать отклонение от первоначального сценария ошибкой само по себе: адаптация может быть правильным решением, если изменилась ситуация или появилась новая информация.

### FR-COACH-03. Сильные действия
Тренер показывает действия, которые помогли пользователю.

### FR-COACH-04. Ошибки
Тренер указывает ключевые ошибки пользователя.

Не просто:

> «Нужно быть увереннее»,

а:

> «На 02:40 ты согласился обсуждать причину своего отсутствия, хотя изначальная стратегическая цель заключалась в фиксации условий повышения. После этого управление разговором перешло к директору».

### FR-COACH-05. Последствия

Для значимых действий тренер должен объяснять:

**действие → изменение ситуации → последствия.**

Это фактически центральный принцип приложенного гайда по судейству.

### FR-COACH-06. Рекомендации

После анализа пользователь получает конкретные рекомендации для повторной попытки или следующего поединка.

Например:

**В следующей попытке:**

1. не начинай сразу с оправдания;
2. сначала уточни, что именно изменилось в позиции директора;
3. связывай каждую уступку со встречным обязательством.

Несколько конкретных действий.

# 17. Повтор прохождения

### FR-REPLAY-01. Переиграть

После анализа пользователь может сразу начать новое прохождение.

### FR-REPLAY-02. Вернуться к подготовке

Пользователь может открыть свою предыдущую карточку, изменить стратегию и после этого сыграть снова.

### FR-REPLAY-03. Сохранение условий

При повторе текущего поединка сохраняются ролевое сочетание и скрытая подготовка AI-оппонента.

То есть нельзя делать так:

**Попытка №1:** директор категорически против.

**Попытка №2:** случайно сгенерировался очень добрый директор.

Иначе пользователь не поймёт, действительно ли новая стратегия сработала.

# 18. Администрирование кейсов
### FR-ADMIN-01. Интерфейс администратора
В MVP должен существовать отдельный административный интерфейс настройки симуляции.

### FR-ADMIN-02. Настройки контекста
Администратор должен иметь возможность задать или изменить предусмотренные кейсом параметры симуляции. Подробнее про [структуру кейса](business/Структура кейса)

### FR-ADMIN-03. Влияние настроек
Изменение параметров администратором должно влиять на конфигурацию симуляции и поведение AI-оппонента.
Настройки не должны существовать только визуально.

### FR-ADMIN-04. Запуск настроенной симуляции
После настройки администратор должен иметь возможность сохранить конфигурацию или запустить её для прохождения пользователем.

### FR-ADMIN-05. Методическая библиотека
Базовые кейсы создаются командой и проходят экспертную проверку перед добавлением в библиотеку.
В MVP не требуется полноценный визуальный конструктор кейсов с произвольным созданием всей структуры с нуля.
